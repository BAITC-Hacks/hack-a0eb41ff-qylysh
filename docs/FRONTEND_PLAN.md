# MoneyGraph: план фронтенда

Этот файл можно передать фронтенд-разработчику или coding agent как самостоятельное задание. Источник решений: [общая переписка](https://chatgpt.com/share/6ab3a8dd-fa44-83eb-833d-e082d365968f). Правила передачи результата и интеграции находятся в [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md).

Готовые самостоятельные задания для каждой главы находятся в [FRONTEND_CHAPTER_PROMPTS.md](FRONTEND_CHAPTER_PROMPTS.md).

## Цель и границы

Собрать рабочее место AML-аналитика: обзор сети, исследование графа, приоритетные клиенты, кластеры, объяснение ролей и ограничений данных. Работать в существующем `frontend/`; проект уже содержит каркас первой главы. Не создавать новый Vite-проект и не заменять рабочую структуру ради соответствия схеме из плана.

Стек: React, TypeScript, Vite, React Router, Axios, SCSS, Cytoscape.js. Не добавлять MUI, Tailwind, Redux, Zustand, Next.js, CSS-in-JS и библиотеку графиков для шести полосок распределения ролей. Использовать существующие компоненты и переменные SCSS.

### Правило автономного выполнения

1. Прочитать этот план, [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md), `frontend/README.md`, текущие файлы и статус Git. Не перетирать чужие изменения.
2. Выполнять главы последовательно. Уже реализованное проверить и отметить как выполненное; не переписывать его без дефекта.
3. После каждой главы выполнить её gate. При ошибке исправить причину и повторить проверку. Не отмечать `PASS` по предположению.
4. Если API бэкенда ещё нет, использовать явный mock mode в service layer. Mock нельзя выдавать за реальные аналитические результаты.
5. Не менять внешний API-контракт в одиночку. Несовпадение записать в отчёте и согласовать через интеграционный план.
6. После всех глав подготовить отчёт: сделано, изменённые файлы, команды и результаты, UI состояния, известные проблемы, расхождения с контрактом. Продолжать до готового результата, если нет внешнего блокера.

## Общие инварианты

- Внешние URL: `/dashboard`, `/network`, `/priority`, `/clusters`, `/methodology`, `/data-limitations`; `/` перенаправляет на `/dashboard`.
- GID является числовым идентификатором. Поиск ведёт на `/network?gid={gid}`. Кластер открывается через `/network?cluster={clusterId}`.
- Роли строго: `coordinator`, `consolidator`, `distributor`, `transit`, `terminal`, `peripheral`. Цвета: фиолетовый, красный, оранжевый, синий, зелёный, серый соответственно.
- `roleScore` означает силу соответствия роли, `priorityScore` — очередь аналитической проверки; оба в диапазоне 0..1. Не называть их вероятностью преступления.
- Frontend получает данные только через `src/api/` и его сервисы. Страницы не вызывают Axios напрямую. `VITE_API_URL` содержит базовый URL с `/api/v1`.
- Для загрузки данных показывать `loading`, `success`, `empty`, `error`. Навигация и общий layout остаются доступными при загрузке и ошибке.
- Примерные цифры в макетах и переписке не являются вычисленным результатом. В real mode показывать только ответ сервера.

## Глава 1. Foundation / MVP Skeleton — уже есть, требуется gate

**Результат:** общий `AppLayout`, `Header`, `Sidebar`, шесть маршрутов, поиск GID, `StatCard`, `Loader`, `EmptyState`, `ErrorState`, заготовки страниц, API client и SCSS design system. Cytoscape установлен, но граф ещё не рисуется.

**Проверить:** переходы по всем маршрутам; числовой и нечисловой GID; состояние active nav; ширину 1366×768; доступность кнопок с клавиатуры; `npm run build`. Если каркас не проходит проверку, исправить перед главой 2.

**Gate:** build успешен, маршруты и поиск работают, нет ошибок консоли. Текущий `README` описывает именно этот этап.

## Глава 2. Overview Dashboard + API Foundation — подробно определена в переписке

**Контракт:** `GET /api/v1/summary` и точный DTO из [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md#замороженный-контракт-summary). Внешний JSON использует `camelCase`. Не переименовывать поля и не подменять реальные данные mock значениями.

**Шаги:**

1. До правок проверить gate главы 1.
2. Добавить TypeScript DTO `SummaryResponse`, `SummaryTopNode`, `SummaryCluster`, используя существующий `Role`.
3. Добавить `SUMMARY: '/summary'` в `src/api/endpoints.ts`; реализовать `getSummary(): Promise<SummaryResponse>` в отдельном service. URL строится относительно `VITE_API_URL`.
4. Добавить `VITE_USE_MOCK_API` в `.env.example`. Переключать mock и HTTP только в service layer. Mock возвращает Promise и хранится отдельно от UI. Значения mock явно пометить как демонстрационные.
5. Добавить hook загрузки с `data`, `loading`, `error`, `refetch`. Исключить очевидное обновление state после unmount.
6. Заменить статичные KPI на данные ответа: Clients=`totalNodes`, Relations=`totalEdges`, Seed clients=`totalSeeds`, Clusters=`totalClusters`. `totalTransactions` показать как вторичную метаинформацию.
7. Показать распределение шести ролей в фиксированном порядке с полосами на SCSS; максимум пять `topNodes` и три `topClusters`.
8. Строка top node ведёт на `/network?gid={gid}`, карточка кластера — на `/network?cluster={clusterId}`, ссылка к списку приоритетов — на `/priority`. `NetworkPage` должен корректно читать оба параметра до появления графа.
9. Общие форматтеры чисел, KZT и score вынести из JSX. Сохранить score как 0..1, отображать с двумя знаками; число транзакций брать из ответа.
10. Реализовать loading, error с повтором запроса, empty при `totalNodes === 0`, success. Не показывать нули как данные во время загрузки.

**Gate:** `npm run build`; вручную проверить четыре состояния в mock mode и, когда бэкенд готов, ответ настоящего `/summary`; переходы по GID/кластеру; keyboard navigation; layout на 1366×768. Сверить JSON поле в поле с [контрактом](INTEGRATION_PLAN.md#замороженный-контракт-summary). Если backend ещё не реализовал endpoint, отметить real mode `NOT VERIFIED`, а не `PASS`.

## Глава 3. Network Graph — следующий этап, составлен из архитектуры переписки

**Результат:** Cytoscape показывает локальный ориентированный граф для выбранного GID или кластера. Не загружать все 2248 узлов как стартовый экран.

**Шаги:** согласовать схемы `GET /nodes/{gid}/graph` и `GET /clusters/{cluster_id}/graph`; добавить DTO и сервисы; отрисовать узлы и направленные рёбра; выделение узла и связей; панель кратких деталей; состояния загрузки, пустого графа, ошибки. `gid` и `cluster` из URL должны сохранять смысл при обновлении страницы. Depth 4 помечать как обрезание наблюдения, не как доказательство конечного получателя.

**Gate:** известный GID и кластер открывают корректные подграфы; направление `src → dst` верно; повторное открытие URL работает; неизвестный GID даёт понятное состояние; размер графа ограничен контрактом; UI не зависает на целевых данных.

## Глава 4. Priority и Node Details — следующий этап

**Результат:** ранжированный список всех узлов с поиском/фильтрами и карточка узла с ролью, score, evidence и измеренными метриками.

**Шаги:** согласовать `GET /top-nodes`, `GET /nodes` и `GET /nodes/{gid}`; добавить DTO и сервисы; серверную пагинацию, сортировку по убыванию `priorityScore` и стабильный tie-breaker по `gid`; фильтры без потери URL state; переход в граф выбранного узла. Evidence показывать как объяснение вычисленных правил, не как обвинение.

**Gate:** первые 20 и последующие записи доступны без дублей; фильтр/поиск/страница согласованы с сервером; неизвестный GID корректно обрабатывается; score совпадает с API.

## Глава 5. Clusters, Methodology, Data limitations — следующий этап

**Результат:** список/карточки кластеров, переход в сеть, понятное описание метода и ограничений исходного 4-хопового графа.

**Шаги:** согласовать `GET /clusters` и `GET /clusters/{cluster_id}`; показать размер, seed count, внутренний объём, top GID и hypothesis; раскрыть метод ролей и ранжирования на странице Methodology; на Data limitations описать период июль 2026, порог ≥5 000 KZT, только исходящие переводы от seed, глубину 4 и отсутствие ground truth labels.

**Gate:** сумма размеров кластеров и общая численность согласованы; переходы работают; методология не обещает недоказанную точность.

## Глава 6. Финальная проверка фронтенда

1. В чистой установке выполнить `npm ci` и `npm run build` на поддерживаемом Node.js (см. `frontend/README.md`).
2. Пройти маршруты, mock mode и real mode. Проверить клавиатуру, пустые/ошибочные ответы и целевую ширину.
3. Сверить DTO с OpenAPI и реальными JSON, особенно casing, nullability, параметры и коды ошибок.
4. Отдать интегратору отчёт по шаблону из [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md#передача-результата-от-разработчиков). Ни один непроверенный пункт не записывать как PASS.

Главы 3–6 являются рабочим планом, выведенным из обсуждённой архитектуры. В исходной переписке подробно сформулированы только главы 1 и 2 фронтенда; перед реализацией следующих глав точные DTO нужно закрепить в интеграционном контракте.

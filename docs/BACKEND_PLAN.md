# MoneyGraph: план бэкенда

Этот файл можно передать backend-разработчику или coding agent как самостоятельное задание. Основа — [обсуждённый план из 12 глав](https://chatgpt.com/share/6ab3a8dd-fa44-83eb-833d-e082d365968f). Общие контракты и передача результатов — в [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md).

## Цель и устройство

Работать в существующем `backend/`. Один Python-кодовый контур: Parquet → загрузка/валидация → NetworkX/аналитика → CSV + SQLite snapshot → FastAPI `/api/v1` → React. SQLite — read model результата, а не место вычисления графовых метрик. Использовать starter из `docs/starter/` как источник проверенных формул, не запускать его вместо приложения без интеграции.

Стек: Python 3.11+, FastAPI, Pydantic v2, pandas, pyarrow, NetworkX, SQLite из стандартной библиотеки, pytest. Go не использовать. Зафиксировать новые зависимости в `requirements.txt` только когда соответствующая глава реально использует их.

### Правило автономного выполнения

1. Прочитать этот план, [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md), `backend/README.md`, `docs/README (1).md` и текущий код. Не перетирать чужие изменения.
2. Главы 1–2 в репозитории уже начаты; проверить их gate и исправить найденный дефект перед следующими главами. Не объявлять их завершёнными до проверки.
3. Идти последовательно через все главы. После каждой главы выполнить gate и исправить ошибки. Если внешний контракт меняется, сначала обновить общий документ и сообщить фронтенду; не делать тихого изменения API.
4. Детерминированный pipeline обязан работать повторно с исходных файлов. Не редактировать Parquet. Не хардкодить результат аналитики из примеров переписки.
5. Отчитываться о фактических командах, результатах и известных проблемах по шаблону интеграционного плана. `PASS` допустим только после выполнения проверки.

## Данные и неизменяемые правила

Источник в `docs/data/`: `nodes.parquet`, `edges.parquet`, `transactions.parquet`. Ожидаемые числа **только для данного набора**: 2248 узлов, 3119 агрегированных рёбер, 4840 транзакций, 81 seed. Узел: `gid`, `depth`, `is_seed`; ребро: `src`, `dst`, `sum_kzt`, `n_tx`, `depth`; транзакция: `src`, `dst`, `date`, `sum_kzt`. Направление — движение денег `src → dst`.

В Parquet/SQLite GID остаётся int64. Во внешнем API его нужно передавать десятичной строкой, включая `gid`, `topGid`, graph `source`/`target` и GID focus: иначе браузер округляет реальные 18-значные значения.

Шесть ролей: `coordinator`, `consolidator`, `distributor`, `transit`, `terminal`, `peripheral`. `role_score` и `priority_score` в диапазоне 0..1, не вероятность преступления. `evidence` детерминированно объясняет измеренные признаки. Глубина 4 означает возможное усечение наблюдения. Изолированные узлы нельзя терять. API не должен утверждать, что роль или кластер являются доказанным преступным поведением.

## Глава 1. Каркас и внутренние схемы — уже есть, требуется gate

**Результат:** структура `app/api`, `analytics`, `schemas`, `services`, `repositories`, `db`, `core`; запуск `uvicorn app.main:app --reload`; `/health`, `/docs`, `/openapi.json`; версия API `/api/v1`; единые внутренние имена `gid`, `role`, `role_score`, `priority_score`, `cluster_id`, `evidence`.

**Gate:** приложение импортируется; health возвращает 200; OpenAPI открывается; Pydantic валидирует роли и score; нет случайно опубликованных domain endpoints без реализации.

## Глава 2. Загрузка и валидация Parquet — уже есть, требуется gate

**Результат:** `analytics/loader.py`, `validator.py`, CLI `python -m app.analytics.check_data --data-dir ../docs/data`; проверка колонок/типов, NaN/inf, неотрицательных сумм и счётчиков, уникального GID и пары ребра, ссылок на существующие узлы, диапазонов depth, согласованности агрегированных рёбер с транзакциями. Для данного набора проверять 2248/3119/4840/81.

**Gate:** корректный набор принимается; повреждённые примеры из тестов отвергаются; CLI выдаёт ненулевой код при ошибке; исходные файлы не изменяются. При чтении другого набора проверку фиксированных чисел можно отключить, структурные инварианты остаются.

## Глава 3. Ориентированный граф

**Шаги:** добавить `networkx.DiGraph`; сначала все GID как вершины, затем рёбра с `sum_kzt`, `n_tx`, `depth`. Сохранить направление `src → dst` и изолированные узлы.

**Gate:** число вершин равно числу GID; число рёбер равно числу уникальных пар; каждый атрибут сверяется с Parquet на выборке; 5 ручных проверок направлений.

## Глава 4. Feature engineering

**Шаги:** использовать вычисления starter там, где они подходят; на каждый GID получить `in_degree`, `out_degree`, `in_kzt`, `out_kzt`, `in_tx`, `out_tx`, `pagerank`, `pass_through`, `truncated_by_depth`, `total_degree`, `total_volume`, `seed_reach_count` и percentiles для degree/volume/PageRank/seed reach. Правило `seed_reach_count` документировать и сделать воспроизводимым.

**Gate:** ровно одна строка на каждый GID; неотрицательные degree/amount; percentiles в 0..1; depth 4 корректно помечен; 5 GID вручную сверены с графом.

## Глава 5. Rule Engine для ролей

**Шаги:** отдельно определить и зафиксировать пороги/precedence для шести ролей. Исходный порядок обсуждения: coordinator → consolidator → distributor → transit → terminal → peripheral fallback. Основание — graph metrics и explainable rules, без обучения на отсутствующих метках. Учесть, что depth 4 с `out_degree=0` не доказывает роль terminal; seed нельзя назвать transit только по `pass_through`.

**Gate:** 100% GID имеют одну допустимую роль; нет null; пограничные случаи покрыты тестами; минимум 3 кандидата на существенную роль проверены вручную. Реальные формулы и пороги записаны в Methodology.

## Глава 6. Role score и evidence

**Шаги:** вычислить `role_score` как силу соответствия правилу 0..1. Для каждого GID построить короткое детерминированное `evidence` из фактических чисел и признаков; не использовать LLM-генерацию для этих текстов.

**Gate:** score и evidence заполнены у всех узлов; текст до 200 символов, числа совпадают с признаками; повторный запуск выдаёт те же значения; проверить выборку 10 GID.

## Глава 7. Кластеры

**Шаги:** исходный граф сохранить ориентированным; для community detection построить undirected view, вес `sum_kzt`, фиксированный seed 42; использовать Louvain. Назначить `cluster_id` каждому узлу. Считать `n_nodes`, `n_seed`, `sum_kzt_internal`, `top_gids`, детерминированную `hypothesis`.

**Gate:** каждый GID в одном кластере; сумма `n_nodes` равна 2248 для данного набора; top GID принадлежит кластеру; повторный запуск сохраняет ID и суммы.

## Глава 8. Priority ranking

**Шаги:** зафиксировать формулу из percentile PageRank, seed reach, role score, volume и degree. Получить `priority_score` для всех GID; сортировка по score DESC с устойчивым tie-breaker по `gid`. Сформировать минимум top 20 для UI, сохранить рейтинг всех узлов.

**Gate:** все score 0..1; сортировка стабильна; список содержит минимум 20; причины высоких мест проверены вручную и соответствуют evidence; результат воспроизводим.

## Глава 9. SQLite snapshot и обязательные CSV

**Шаги:** создать `nodes`, `edges`, `clusters`, `transactions` в `analysis.db`; индексы по `nodes.gid`, `role`, `cluster_id`, `priority_score`, `edges.src`, `edges.dst`. Сохранять метрики и объяснения в `nodes`. Экспортировать `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` по фиксированной схеме. Повторный запуск должен заменять snapshot атомарно или безопасно, без дублей.

**Gate:** база создаётся с нуля; числа строк сверены с Parquet; случайные 20 GID совпадают в DataFrame, SQLite и CSV; повторный запуск не дублирует данные.

## Глава 10. Внешний API contract

**Шаги:** закрепить Pydantic response models для summary, списка/карточки узлов, графа, кластера и пагинации. Для `/summary` точный `camelCase` DTO уже задан в [INTEGRATION_PLAN.md](INTEGRATION_PLAN.md#замороженный-контракт-summary), включая nullable `topGid`. Внутренние DataFrame/SQLite поля остаются `snake_case`; сериализацию наружу делать явно. Для остальных endpoint сначала утвердить поля, query параметры, nullability и коды ошибок в общем контракте, затем писать handlers.

**Gate:** образцы JSON валидируются Pydantic и TypeScript DTO; OpenAPI соответствует спецификации; спорные поля не замалчиваются. Передать фронтенду контракт до реализации запросов.

## Глава 11. FastAPI endpoints

**Маршруты:**

```text
GET /api/v1/summary
GET /api/v1/nodes
GET /api/v1/nodes/{gid}
GET /api/v1/nodes/{gid}/graph
GET /api/v1/top-nodes
GET /api/v1/clusters
GET /api/v1/clusters/{cluster_id}
GET /api/v1/clusters/{cluster_id}/graph
```

`/nodes`: фильтры role, cluster, minPriority, isSeed, search, page, limit после согласования точного написания. Граф отдаёт `{ "nodes": [], "edges": [] }` с ограниченным размером локального фрагмента. API читает готовый snapshot, не пересчитывает аналитику на запрос. Настроить CORS для локального Vite origin или Vite proxy и зафиксировать выбранный способ в README.

**Gate:** 200 для известных записей, 404 для отсутствующих ресурсов, 422 для неверных параметров, осмысленный пустой список, без лишних DB полей; OpenAPI и фактический JSON совпадают.

## Глава 12. Сквозная и регрессионная проверка

**Шаги:** на отдельном временном output path пересоздать snapshot из исходных Parquet, CSV и SQLite; проверить данные, роли, score, кластеры и API. Сравнить ответы с DTO фронтенда. Не удалять рабочие результаты других участников.

**Gate:** 2248 GID, уникальность, шесть допустимых ролей, score 0..1, заполненные cluster/evidence, top ≥20, известный/неизвестный GID 200/404, граф с узлами и рёбрами, стабильная сортировка, все обязательные CSV. Выполнить `pytest`; подготовить отчёт для интегратора.

# MoneyGraph: правила совместной разработки и план интеграции

Этот документ — общий контракт и самостоятельное задание третьему участнику после передачи веток фронтенда и бэкенда. Планы исполнителей: [FRONTEND_PLAN.md](FRONTEND_PLAN.md) и [BACKEND_PLAN.md](BACKEND_PLAN.md). Основа решений — [переписка проекта](https://chatgpt.com/share/6ab3a8dd-fa44-83eb-833d-e082d365968f).

## 1. Кто что делает

| Участник | Свои файлы | Обязан передать |
|---|---|---|
| Frontend | `frontend/**` | рабочую ветку/commit, результат build, список UI-проверок, DTO и использованные endpoint |
| Backend | `backend/**` | рабочую ветку/commit, результат pytest/pipeline, OpenAPI, реальные примеры JSON и путь к snapshot |
| Интегратор | `docs/**`, совместные фиксы в `frontend/**` и `backend/**` после получения веток | единый работающий flow и итоговый отчёт |

Каждый работает в своей ветке или worktree. Не копировать поверх рабочей папки другого участника. Общие контракты меняются через отдельное согласованное изменение документа; при интеграции менять обе стороны в одном commit или серии явно связанных commits.

## 2. Общие правила

1. Истина о данных — исходные Parquet и вычисленный backend snapshot. Макетные значения и примеры JSON служат только для формы ответа.
2. API имеет prefix `/api/v1`. `GET /health` находится вне prefix. Frontend задаёт `VITE_API_URL=http://localhost:8000/api/v1` и вызывает относительные пути вроде `/summary`.
3. В Python/SQLite внутренние имена `snake_case`. В закреплённом внешнем `/summary` JSON — `camelCase`; преобразование выполняет backend. Остальные DTO фиксируются до реализации их handlers. Нельзя полагаться на автоматическое преобразование, пока оно не проверено тестом.
4. GID — целочисленный идентификатор в Parquet и SQLite, но десятичная строка во внешнем JSON и TypeScript. Все 2248 GID этого набора превышают `Number.MAX_SAFE_INTEGER`; передача JSON number меняет значение в браузере. URL принимает ту же десятичную строку. Роли — шесть значений из планов. Score — число 0..1. `null` допустим только там, где это прямо указано контрактом.
5. Даты/объём/роли отражают только наблюдаемый набор: июль 2026, 81 seed, исходящие переводы, 4 хопа, порог ≥5 000 KZT. Отсутствие наблюдаемого ребра не доказывает отсутствие реальной связи.
6. Изменение имени поля, типа, nullability, query параметра, кода ошибки или endpoint требует обновления этого документа, backend schema/OpenAPI, frontend DTO/service и проверки в одном интеграционном цикле.
7. `PASS` ставится только после фактического выполнения команды или ручной проверки. Для недоступного backend/mock/браузера писать `NOT VERIFIED` с причиной. Каждый обнаруженный сбой исправлять и повторять соответствующий gate.

## 3. Замороженный контракт summary

Это единственный подробно закреплённый в переписке внешний DTO на момент составления документа:

```http
GET /api/v1/summary
Content-Type: application/json
```

```ts
type Gid = string // decimal digits; never convert to JavaScript number

type Role =
  | 'coordinator' | 'consolidator' | 'distributor'
  | 'transit' | 'terminal' | 'peripheral'

interface SummaryTopNode {
  rank: number
  gid: Gid
  role: Role
  priorityScore: number
  clusterId: number
  evidence: string
}

interface SummaryCluster {
  clusterId: number
  nodeCount: number
  seedCount: number
  internalVolumeKzt: number
  topGid: Gid | null
  hypothesis: string
}

interface SummaryResponse {
  totalNodes: number
  totalEdges: number
  totalTransactions: number
  totalSeeds: number
  totalClusters: number
  roles: Record<Role, number>
  topNodes: SummaryTopNode[]
  topClusters: SummaryCluster[]
}
```

Проверки: сумма `roles` равна `totalNodes`; `totalClusters` равно числу кластеров в snapshot; `topNodes` отсортированы по `priorityScore` DESC; `rank` начинается с 1; score 0..1; `topGid` принадлежит кластеру, если не `null`. Пример из переписки содержит выдуманные распределения и не считается эталоном чисел.

**Интеграционное уточнение:** исходное предложение переписки использовало `number` для GID. Реальные 18-значные значения делают этот тип неточным в JavaScript, поэтому совместный внешний контракт заменён на `Gid = string` во всех ответах и URL. Backend сериализует внешние ответы в `camelCase`; внутренние аналитические поля остаются `snake_case`.

## 4. Реестр остальных endpoint

| Endpoint | Назначение | Статус контракта |
|---|---|---|
| `GET /api/v1/nodes` | поиск/фильтры/пагинация | поля, query и ошибки уточнить до реализации |
| `GET /api/v1/nodes/{gid}` | детали узла | внешний DTO уточнить |
| `GET /api/v1/nodes/{gid}/graph` | локальный граф узла | лимиты и DTO уточнить |
| `GET /api/v1/top-nodes` | рейтинг | пагинацию и сортировку уточнить |
| `GET /api/v1/clusters` | список кластеров | внешний DTO уточнить |
| `GET /api/v1/clusters/{cluster_id}` | кластер | внешний DTO уточнить |
| `GET /api/v1/clusters/{cluster_id}/graph` | подграф кластера | лимиты и DTO уточнить |

Зарезервированное имя endpoint не означает, что он уже работает. Перед реализацией каждой пары frontend/backend интегратор или разработчики дописывают в этот раздел: точный JSON, query path, nullability, сортировку, пагинацию, 404/422, пример ответа. Сначала контракт и fixture, затем обе реализации, затем field-by-field проверка.

## 5. Параллельный порядок работ

1. **Общий старт:** обе стороны читают три плана и фиксируют summary DTO. Backend проходит свои главы 1–2; frontend — главу 1. Эти gates не требуют друг друга.
2. **Параллельно:** frontend делает главу 2 на mock service, backend делает главы 3–9 и готовит snapshot. Mock mode не должен скрывать отсутствие реального API.
3. **Точка стыка:** backend реализует главы 10–11, начиная с `/summary`; frontend переключает `VITE_USE_MOCK_API=false` и сверяет ответ. Новые endpoint вводятся по одному после фиксации DTO.
4. **Передача интегратору:** каждый присылает commit hash/ветку и отчёт. Интегратор объединяет изменения, затем выполняет раздел 6.

## 6. Задание интегратору: выполнить до рабочего результата

1. Прочитать этот документ, оба плана, отчёты разработчиков и `git status`. Сохранить незакоммиченные правки. Объединить ветки обычным merge/rebase по правилам команды; конфликты решать на основе зафиксированного контракта, не принимать одну сторону автоматически.
2. Установить поддерживаемые версии Python и Node.js, указанные в README, затем зависимости из lock/requirements. Использовать отдельное окружение. Проверить `node --version` перед `npm ci`: текущая локальная среда при подготовке плана показывала Node 18.17.1, а frontend требует Node 20.19+ или 22.12+.
3. Из `backend/` выполнить `python -m app.analytics.check_data --data-dir ../docs/data`, затем pipeline на отдельном output path, `pytest`, проверить CSV/SQLite и реальные `/health`, `/openapi.json`, `/api/v1/summary` и остальные реализованные endpoints.
4. Из `frontend/` выполнить `npm ci`, `npm run build`; запустить frontend и backend одновременно в real mode. Проверить CORS/proxy, URL, загрузку Dashboard, GID поиск, граф, Priority, Clusters, Methodology, Data limitations и переходы между ними согласно реально завершённым главам.
5. Для каждого endpoint сравнить фактический JSON с TypeScript DTO и OpenAPI: точные имена полей, типы, nullability, порядок/пагинация, ошибки 404/422. Особое внимание `/summary` и `camelCase`.
6. Проверить UI состояния `loading/success/empty/error`, затем smoke test на известном GID, неизвестном GID, кластере и пустом результате. Проверить цифры Dashboard против SQLite/CSV.
7. Любую воспроизводимую ошибку исправить в правильном слое, повторить gate и описать причину. Не менять методику аналитики для подгонки UI. Не выдавать mock mode за успешную интеграцию.
8. Подготовить итоговый отчёт по разделу 7. Завершить только когда сквозной путь Parquet → snapshot → API → React проверен либо есть конкретный внешний блокер с командой/логом для воспроизведения.

Этот раздел — инструкция для будущего этапа. В текущей задаче интеграция и запуск по просьбе пользователя отложены.

## 7. Передача результата от разработчиков

Каждый исполнитель передаёт короткий Markdown отчёт в своей ветке или в описании PR:

```text
Сторона: frontend | backend
Ветка / commit:
Завершённые главы и gates:
Изменённые файлы:
Команды и фактические результаты:
API/DTO, которые реализованы:
Mock или real mode:
Не проверено и почему:
Известные проблемы с шагами воспроизведения:
```

Финальный отчёт интегратора содержит: merge commits, исправленные несовпадения, команды и результаты backend/frontend, матрицу endpoint `PASS/FAIL/NOT VERIFIED`, проверенные UI состояния, результат сквозного сценария и оставшиеся блокеры. Не писать `PASS`, если проверка не запускалась.
